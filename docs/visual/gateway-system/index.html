MyZubster Gateway — Integration & Verification Boundary

Architecture view derived from the public Gateway README. It separates application flow from settlement verification and runtime proof.

API Surface

Health, auth, users, orders, payments, webhooks and registry routes.

Repository documentation describes these as main areas; current router/controller source remains authoritative.

Gateway / Adapters

Backend integration boundary between MyZubster core and external providers.

Node.js + Express + MongoDB/Mongoose + configured provider integrations.

Settlement Lifecycle

PENDING → RESERVED/ACCEPTED → SUBMITTED → CONFIRMED → PAID

Failure/dispute/cancel states remain possible.

Independent Verification

Transaction/hash, recipient, asset, network and canonical amount must match expected settlement data.

Unavailable verification should fail closed.

Runtime evidence boundary

The repository describes the Gateway as MVP / active validation. A repository, API route, workflow, provider response or database update is not enough to prove an external payment or production deployment. Runtime/deployment claims require separate evidence.

Guardrails: database update ≠ chain/payment proof · provider response ≠ PAID · MYZ internal ledger ≠ automatic on-chain transaction · configured integration ≠ production readiness · health endpoint existence ≠ healthy production runtime.
