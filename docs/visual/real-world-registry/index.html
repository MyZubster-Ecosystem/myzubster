VISUAL #015 · EVIDENCE-FIRST

Registry / Real-World Observation

A real-world observation becomes useful only when the observation, structured metadata, review state and publication boundary remain distinguishable.

← Visual Hub

Observation pipeline

  1. 01OBSERVE
    authorized real-world subject/event
  2. 02DOCUMENT
    media, caption, timestamp, permitted location/data
  3. 03CONNECT
    map, garden, registry, project, dataset or bounty
  4. 04REVIEW
    criteria, provenance, privacy and quality checks
  5. 05VERIFY
    claim bounded by available evidence
  6. 06PUBLISH
    sanitized snapshot / reusable public data

Core observations

MyZubster documents real-world observations including places, environmental data, plants, services and authorized media.

Status: Development / validation.

Marketplace context

Garden and sensor APIs can provide structured context for environmental observations.

Boundary: endpoint existence does not prove field deployment or sensor accuracy.

Public snapshots

Sanitized information may be published as reusable snapshots, including content-addressed publication tracks.

Boundary: CID/file existence does not prove truth of the underlying real-world claim.

Evidence boundaries

Photo ≠ verified fact

A photo proves that a file exists and may document a scene; it does not automatically verify species, ownership, exact location, time or event.

Registry row ≠ physical truth

A database or API record is application evidence. Physical claims require the relevant observation and review evidence.

Map point ≠ permission

Location data must be authorized and privacy-safe. Sensitive or unnecessary precise locations should not be published.

Publication ≠ blockchain settlement

Public snapshots, IPFS/IPNS references and internal MYZ accounting remain separate from any external settlement rail.

Rule: OBSERVATION → EVIDENCE → REVIEW → SANITIZED PUBLICATION. No layer silently upgrades the previous one.
