# MyZubster Life — External Ecosystems

## Purpose

MyZubster Life can provide voluntary entry paths for people who participate in independent open-source ecosystems while keeping identity, governance, authentication, licensing and project affiliation explicit.

A fork, issue, pull request, link or technical integration does **not** make an external person or organization a MyZubster member or partner.

## Ecosystem map

### Open-source / open-standard ecosystems

- **Vircadia World** — experimental metaverse interoperability target.
- **Decentraland SDK** — experimental scene/ECS/toolchain interoperability target.
- **Immersive Web / WebXR** — browser XR and open-standard interoperability target.

People from these communities may voluntarily enter MyZubster Life through the same public contributor onboarding available to everyone. Their upstream identity must not be imported or claimed without their action and consent.

### Infrastructure providers

- **Aruba S.p.A.** — exploratory infrastructure provider candidate.

Aruba is not classified as an open-source community or an existing MyZubster partner. Any future use of Aruba services must be represented as a provider integration unless an explicit agreement supports a stronger claim.

## Life gateway roles

External participants enter with no privileged role by default.

- `visitor` — explore public Life surfaces.
- `contributor` — propose public content, code, translations, characters or observations through the normal contribution workflow.
- `creator` — build compatible experiences after normal project review.
- `maintainer` — granted explicitly by MyZubster governance; never inferred from upstream status.
- `admin` — never granted through an external ecosystem gateway.

## Identity boundary

An upstream GitHub username, avatar, profile, wallet, Decentraland identity, Vircadia identity, XR runtime identity or provider account is not automatically a MyZubster identity.

Linking identities must be voluntary, explicit and technically verifiable where verification is offered.

## Provenance

For every external integration MyZubster should record, where applicable:

- upstream project/provider;
- canonical repository or official provider URL;
- version, branch or commit used;
- license and asset-license requirements;
- integration status;
- related upstream issue/PR;
- whether upstream maintainers have accepted a contribution;
- whether any partnership or endorsement evidence exists.

## Status vocabulary

- `exploratory` — being evaluated; no integration or affiliation implied.
- `experimental` — technical work exists but is not necessarily accepted upstream.
- `upstream_validated` — relevant contribution has been accepted upstream; this still does not imply partnership.
- `partner` — use only when explicit evidence of partnership exists.

## Current principle

MyZubster should interoperate with external ecosystems rather than absorb them. External communities retain their own governance, identity, licenses and infrastructure boundaries.
