# MyZubster Identity Genesis Bounty v0.1

The **Identity Genesis Bounty** rewards a participant for creating a public-safe MyZubster profile and a narrative character that can later be used in the MyZubster metaverse.

This bounty does **not** prove civil/legal identity, authorship, ownership, employment, or any external real-world claim.

## Reward

Default prototype reward:

- asset: `MYZ`
- amount: `100`
- meaning: internal MyZubster reward/accounting units
- trigger: successful human review

The amount is configurable with:

```bash
IDENTITY_BOUNTY_REWARD_MYZ=100
```

A recorded MYZ reward is not an XMR transfer, token transfer, or promise of monetary value.

## API

Public participant endpoints:

```text
GET  /api/identity-bounties/definition
GET  /api/identity-bounties/stats
POST /api/identity-bounties/claim
POST /api/identity-bounties/:id/update
POST /api/identity-bounties/:id/submit
GET  /api/identity-bounties/:id
```

Reviewer endpoints:

```text
GET  /api/identity-bounties/review/queue
POST /api/identity-bounties/:id/review
```

Reviewer endpoints fail closed until this environment variable is configured:

```bash
IDENTITY_BOUNTY_REVIEW_TOKEN=<secret stored outside Git>
```

The token must never be committed to the repository.

## Identity boundary

v0.1 creates an `account-unverified` identity record for the bounty workflow.

A participant may request a public MYZ-ID string, but that string is **not** cryptographically verified and must not be treated as proof of identity.

Future MYZ-DCR integration should replace the browser-generated participant key with an authenticated account identifier and then add a cryptographic challenge/signature step before any `verified` identity state can be granted.

## Privacy boundary

Never submit:

- private keys;
- seed or mnemonic phrases;
- passwords;
- access tokens;
- identity documents;
- passport or national ID data;
- private recovery information.

The prototype rejects common secret field names and obvious secret material before storage, but this filter is defense-in-depth only. It is not a substitute for authenticated sessions, moderation, data-minimization review, and production security testing.

## Anti-abuse boundary

The prototype allows one submission per `participantKey` and bounty version.

Today the participant key can be generated by the browser, therefore it is **not strong Sybil resistance**. Before a broad public reward program, replace this with authenticated accounts and add abuse controls such as account age/rate limits, moderation, duplicate-content detection, and a review audit trail.

## Metaverse integration

The intended user journey is:

```text
Identity Bounty
    -> public profile
    -> character
    -> review
    -> MYZ reward recorded
    -> enter Neon Plaza
    -> future verified MYZ-DCR linkage
    -> personal comic / story timeline
```

The metaverse may display a profile or MYZ-ID, but display must remain distinct from cryptographic verification.
