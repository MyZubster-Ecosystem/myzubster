# MyZubster Governance — Draft RFC

> **Status: PROPOSAL ONLY.** This document is not an adopted constitution, operational DAO, or binding compensation agreement. See [RFC discussion #1617](https://github.com/MyZubster-Ecosystem/myzubster/issues/1617).

## Purpose
Coordinate a federation of independent contributors, projects and infrastructure nodes while preserving autonomy, public evidence, security and financial sustainability.

## Current practice versus proposed model
**Current:** GitHub issues, pull requests, maintainers' repository permissions, tests and documented contributions are the practical coordination mechanisms. An independently operated node does not imply an operational DAO or decentralized voting system.

**Proposed for discussion:** public requests for comments (RFCs) for cross-project changes, explicit ownership of decisions, voluntary node participation, and recorded outcomes.

## Decisions
1. **Local project/node decisions:** the owner controls their own deployment, budget and data, subject to any voluntary interoperability commitments and applicable law.
2. **Repository changes:** open an issue/PR; reviewers evaluate tests, privacy and security; only authorized maintainers approve and merge.
3. **Cross-node interoperability, shared services or policy:** publish an RFC stating problem, options, security/privacy impact, affected maintainers, financial impact and rollback. Invite comments for a **proposed** seven-day period (longer for major changes). Record a reasoned decision and explicit consent from affected owners. Silence is not consent.
4. **Urgent security incidents:** use a private reporting channel and existing maintainer authority; document a safe public postmortem afterward.

## Participation
Anyone may propose an issue or RFC and submit a PR. Contribution does not automatically confer merge permissions, control of other nodes, financial authority or voting rights. Any future DAO voting design requires a separate proposal.

## Disagreements and conflicts
Prefer evidence-based review and a documented attempt at mediation. Escalate unresolved repository questions to authorized maintainers. Declare relevant conflicts of interest. Do not disclose private keys, infrastructure credentials or user data in public issues.

## Infrastructure, payments and MYZ
Operating a node, contributing funds, accepting bounty tasks and providing services are voluntary and require explicit agreement. No shared costs, payments, profit percentages, MYZ redemption value or rewards are guaranteed by this draft. Any budget must state funding source, authorized approver, limits and reporting, and be reviewed for legal/tax implications before commitment.

## First governance pilot
Use [issue #1617](https://github.com/MyZubster-Ecosystem/myzubster/issues/1617) to gather feedback from Nicola, Wasim and other contributors. Select one low-risk, non-production interoperability/documentation decision. Record options, objections, named volunteers, maintainer decision and public evidence of the outcome.

## Questions to resolve before adoption
- Which changes require consent from all affected node operators?
- Who approves shared budget commitments, and with what spending cap?
- How are maintainers selected, replaced or recused?
- How are contribution evidence, bounty eligibility and appeals verified?
- What future voting or DAO structure, if any, would be appropriate?

## Adoption
This document takes effect only after contributor review, an explicit recorded maintainer decision and a merged PR. Until then existing repository permissions and agreements remain unchanged.
